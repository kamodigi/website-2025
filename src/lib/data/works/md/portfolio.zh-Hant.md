## 關於本網站

這是米谷拓哉的作品集網站（也就是本網站）。使用 SvelteKit 和 TypeScript 構建，介紹個人開發的作品和技術棧。這次在開發中引入了 AI，嘗試用 Gemini CLI 和 Kiro 進行 AI 驅動開發。

## 技術選型

### 選擇 SvelteKit 的理由

採用 SvelteKit，很大程度上是因為這是我個人喜歡的框架。原因在於，Svelte 的設計就像是 HTML 和 CSS 的擴充。我也喜歡 React，它全部用 JS 完成，這是它的優點；但 Svelte 的寫法感覺像是 HTML 的自然延伸，寫起來很舒服。

另外，Svelte 編譯後會變成沒有額外開銷的 HTML、CSS 和 JavaScript，這也是我選擇它的理由。React 和 Vue 需要執行環境（runtime），我認為對小型 Web 應用程式來說過於繁重。此外，Svelte 使用 JavaScript 函式庫時不需要包裝層，這一點也很有吸引力。

### 沒有採用 TailwindCSS 的理由

這次沒有採用 TailwindCSS。我本來就對 Tailwind 持懷疑態度。把樣式寫在類名裡，偏離了語義分離的原則。另外，如果要用預設之外的值，就需要寫 JIT（Just-In-Time）的語法；既然如此，我覺得直接寫 CSS 就好了。

而且近年來可以藉助生成式 AI，不使用特殊語法也能輕鬆寫出原生 CSS。我感覺這一變化大大降低了傳統 CSS 編寫的門檻。

## AI 驅動開發的實踐

在這個專案中，我嘗試了使用 Gemini CLI 和 Kiro 的 AI 驅動開發。不過實際上，更多的工作流程是先讓 AI 寫程式碼，再由我自己手動修改大約三成。

特別頭疼的是，Gemini 經常不按本專案使用的 SvelteKit v5，而是按 v4 的語法來寫。另外，AI 似乎幾乎不瞭解 Paraglide JS，所以多語言相關的部分全部由我自己編寫。

我深切體會到，AI 驅動開發並不是完全自動化的；只有由人對 AI 生成的程式碼進行恰當的審查和修改，它才會成為真正可用的程式碼。尤其是對於新版本的函式庫或小眾的函式庫，AI 的知識往往跟不上，因此人的判斷不可或缺。

## 實作細節

### 使用 Three.js/Threlte 實作互動式主視覺

在這個作品集中，我特別在首頁的主視覺上下了功夫。利用 Three.js（準確地說是 Svelte 實作的 Threlte），製作了動態的幾何圖案。此外，還實作了響應使用者點擊的互動效果。

這是我第一次接觸 Three.js，正好是從基礎開始學習 3D 圖形的好機會。WebGL 的原理、著色器的概念、3D 空間中的座標系等，我學到了很多新知識。今後也想積極地在 Web 上運用 3D 表現。

### 用 Markdown 管理內容

作品資訊用 Markdown 檔案管理。在前置資料（Front Matter）中寫中繼資訊，正文則可以作為技術文章來閱讀。

用 Markdown 管理與 Git 的配合非常好，版本管理也很容易。變更歷史便於追蹤，差異也能清楚地確認。比起使用 CMS 更簡單，我覺得對工程師來說是很好用的機制。

中繼資訊同時準備了日語和英語兩種版本，並與 Paraglide JS 配合，實現了多語言支援。

## 部署與基礎設施

### Coolify 與日本國內基礎設施的選擇

部署選擇 Coolify，是因為我最近自己租了伺服器並在上面執行 Coolify。Vercel 也是很有吸引力的部署平台，但我特意選擇 Coolify，是因為可以使用日本國內的基礎設施。

日本的數位貿易逆差在不斷擴大，作為 IT 從業者，這是我關心的社會問題。我自己能做的，只是藉助開源軟體嘗試使用日本國內的基礎設施；但如果這種做法能推廣開來，我認為可以成為應對日本數位貿易逆差的一種對策。這雖然只是個人的一個小選擇，但我把它看作履行技術人員社會責任的一種方式。

## 開發中遇到的困難

開發中遇到的困難主要在設計和 UI/UX 方面。我沒有學過設計，所以一邊尋找可以參考的網站設計，一邊摸索著推進。當然，生成式 AI 也幫了很大的忙。

比起技術實作，我更深刻地體會到，做出既好用又美觀的介面有多難。設計中有很多感性的部分，也沒有唯一的正確答案，所以一直在不斷試錯。

## 今後的展望

我想把這個作品集打造成發布自己作品的地方。今後開發的工具和應用程式的資訊都會彙總在這裡，把它培育成一個平台。

另外，我也打算在技術文章的寫作上多下功夫。把開發中獲得的見解和試錯的過程用語言表達出來，既能加深自己的理解，也希望提供對其他開發者有幫助的內容。

這個作品集網站本身也會持續改進，並作為嘗試新技術的實驗場來使用。
